# Design Decisions

Why things are built the way they are. Each entry: the choice, the alternatives considered, and why. For the step-by-step build log and bugs found, see [`PLAN.md`](./PLAN.md).

## Container registry: Swarm stack on the routing mesh, not a Traefik domain

In cluster mode Dokploy needs a registry that every node can pull from. We deploy it as a Dokploy Compose resource of type **Stack** (a Swarm service, pinned to the manager node since its storage volume is node-local), with port 5000 published through Swarm's routing mesh. That makes the registry reachable on every node's own loopback address, `127.0.0.1:5000` (not `localhost:5000`, see [Registry address](#registry-address-127001-not-localhost) below), and Docker allows plain-HTTP registries on loopback addresses by default, so nodes need no TLS certificates, no `insecure-registries` entry in `daemon.json`, and no per-node setup at all. A newly joined worker can pull immediately, and the address doesn't depend on the control plane's IP, which changes on every rebuild. The alternative was to run it via plain `docker-compose` on one node and expose it through a Traefik domain (which is how Dokploy's own "Docker Registry" template works). That's closer to a production setup, but without a public domain there's no trusted certificate, so every node would need either a self-signed CA in `/etc/docker/certs.d/` or an `insecure-registries` entry plus a Docker restart. That per-node step would have to be added to `02-launch-worker-vms.sh` and redone whenever the IP changes. The tradeoff we accept: port 5000 is open on every node's IP (so the registry should use auth) and traffic between nodes is plain HTTP, which is fine for a local lab and would not be for production.

## Registry placement: pinned to the manager node

The registry stores images in a named volume, and named volumes are local to the node they were created on — every node has its own, separate, empty `registry-data`. Without a placement constraint, Swarm is free to reschedule the registry task onto a different node (after a reboot, redeploy, or crash), where it would start healthy but with an empty volume: previously pushed images are silently gone and the next deploy fails to pull. So the registry has to be pinned to **one fixed node**. We use `node.role == manager` because the cluster has exactly one manager, the control plane, and it's the one node that is never removed for scaling purposes — workers come and go, so a registry on a worker would lose its images whenever that worker is torn down. The volume therefore lives as long as the cluster does; it does not survive `teardown.sh`, which deletes the control plane too, but images are rebuildable artifacts, so that's acceptable. The routing mesh means placement doesn't affect reachability — `127.0.0.1:5000` works from every node wherever the task runs. Alternatives: a node label (`node.labels.registry == true`) would state the intent explicitly and let the registry run on a worker to take load off the control plane (which already runs Dokploy, its Postgres and Traefik in 2 GB), at the cost of a labelling step in the scripts; pinning by hostname works but ties the config to a VM name. The proper fix is shared storage — the registry supports an S3 storage driver, which would remove the need for pinning entirely and even allow multiple replicas — worth revisiting once object storage is part of the cluster.

## Registry storage: the control plane's disk, sized up to 30G

Pinning the registry to the manager puts its images on the control plane's disk, which was the same 10G every VM gets. That's too small. The Ubuntu base plus Dokploy's own images (Dokploy, Postgres, Redis, Traefik) take roughly 4–5 GB before anything is deployed. In cluster mode Dokploy also **builds every image on the manager** and then pushes it, so each app version costs disk twice there: once as the local image and build cache, and once as compressed layers in `registry-data`. The registry never deletes old layers by itself either; `registry garbage-collect` only frees space after tags are deleted, which is why the stack sets `REGISTRY_STORAGE_DELETE_ENABLED`. The decision: keep the local volume, and give the control plane its own `CP_DISK` (default 30G, `--cp-disk` in `bootstrap.sh`) while workers stay at `DISK=10G`. Multipass disks are sparse, so the bigger disk only takes host space as it actually fills. Alternatives: a different storage backend doesn't pay off yet. An in-cluster MinIO would sit on a node-local volume too and need the same pinning, so it only moves the problem. Real S3 outside the cluster would remove the pinning (see above), but a laptop lab doesn't have one. Keeping 10G and relying on garbage collection plus Dokploy's docker cleanup would work until a few rebuilds of a real app fill the disk, which would likely happen mid-demo.

## Registry auth: generated credentials, htpasswd as a Swarm config

Because port 5000 is open on every node's IP, the registry uses htpasswd auth. `03-setup-registry.sh` generates the credentials on first run into `.registry-credentials` (gitignored). Like `.dokploy-api-key`, they're tied to one cluster instance, so `teardown.sh` removes them. The bcrypt htpasswd file is created on the control plane and handed to the service as an **external Swarm config**. That's Swarm-native, and it doesn't depend on a host path existing wherever the task runs. Swarm configs are immutable, so the config is named after a hash of the credentials: new credentials mean a new config name and a stack update, not a clash with the one in use. The alternative was Dokploy's file-mount API plus a bind mount of `../files/htpasswd`. That would make the file visible in Dokploy's UI, but it relies on a host path on the manager. Dokploy's registry entry is created only after the registry answers, because `registry.create` runs `docker login` immediately.

## Registry address: `127.0.0.1`, not `localhost`

The original plan was `localhost:5000`. It worked from every worker, but `docker push localhost:5000/...` from the control plane hung with `Client.Timeout exceeded while awaiting headers`, while `127.0.0.1:5000` answered instantly. The cause is a known Docker bug, [moby/moby#53091](https://github.com/moby/moby/issues/53091) (present since at least 26.x): Ubuntu resolves `localhost` to `::1` first, and the Swarm routing mesh only redirects IPv4, so on Docker < 29.8.0 an IPv6 connection to a published Swarm port lands on a socket `dockerd` holds just to reserve the port, which accepts it and never answers (`ss` shows `dockerd` on `*:5000` with a non-zero `Recv-Q`). It was fixed in Docker 29.8.0 by [moby/moby#53118](https://github.com/moby/moby/pull/53118), which puts a `docker-proxy` on the IPv6 port instead. That's exactly why only the control plane was affected: Dokploy's installer hardcodes Docker **28.5.0** (and `apt-mark hold`s it), while `02-launch-worker-vms.sh` gives workers the latest from `get.docker.com` (29.8.1 at the time). Reproduced identically on both team members' hosts (WSL2 and macOS), so it has nothing to do with the host OS — everything happens on the VM's own loopback.

Options considered: (a) use `127.0.0.1:5000` — Docker treats all of `127.0.0.0/8` as an allowed plain-HTTP registry, so nothing else changes, and it's what Docker's own swarm tutorial uses; (b) pin every node to Docker ≥ 29.8.0 by installing it on the control plane before Dokploy's installer runs (the installer skips its own Docker install if one exists) — fixes the bug and the version skew at once, but runs Dokploy's own server on a Docker version Dokploy doesn't test (it only uses 29.x — 29.4.2 — for Ubuntu 26.04 remote servers, [Dokploy#4660](https://github.com/Dokploy/dokploy/pull/4660)); (c) upgrade the control plane's Docker after install — takes Dokploy down and is a manual patch applied after setup, which makes rebuilds less reproducible; (d) disable IPv6 binding in `daemon.json` — a workaround that hides the cause. We chose **(a)**: low risk, low reward, and it keeps us on Dokploy's tested Docker version with the deadline in mind. The cost is one rule to remember — never write `localhost` for the registry (Dokploy settings, image tags, CI workflows). Worth revisiting once Dokploy moves its pin to ≥ 29.8.0; at that point switching back to `localhost` is a config change.

Takeaways:
- **Version skew hides bugs.** The same command worked on one node and hung on another purely because of the Docker version, which made the cause hard to spot. With every node on the same explicitly pinned version, it would have failed (or worked) the same way everywhere. Pinning workers to the control plane's version is still open (see the version-mismatch note in `PLAN.md`), and [Dokploy#4722](https://github.com/Dokploy/dokploy/issues/4722) reports that 28/29 skew between Swarm nodes can also break overlay networking.
- **`localhost` is not the same as `127.0.0.1`.** On modern Linux it usually resolves to IPv6 first, so any IPv4-only component in the path fails in ways a plain IPv4 test never shows. When debugging, test `localhost`, `127.0.0.1` and `[::1]` separately.
- **Read what your installer actually does.** The Docker version wasn't a Dokploy setting or documented anywhere we'd looked; it was a hardcoded, apt-held constant in `install.sh`.
- **Check upstream before working around.** Searching Docker's issue tracker turned a confusing hang into a known, already-fixed bug with a precise version boundary, which is what made the options above concrete.
- **Upstream gap.** As of 2026-09-23 there's no Dokploy issue about this; the same 28.5.0 pin is also what breaks Ubuntu 26.04 installs ([Dokploy#5471](https://github.com/Dokploy/dokploy/issues/5471)). Reporting it, with the reproduction above and the upstream fix, is a possible open-source contribution.

## Dokploy's Server IP: set to the control plane's VM IP, not the auto-detected public IP

Dokploy generates app domains (the "generate" button, e.g. `<appName>-<hash>-<ip>.sslip.io`) from its web-server **Server IP** setting (`generateTraefikMeDomain` in `packages/server/src/services/domain.ts`), which is filled in by asking an external service for the machine's public IPv4. That assumes the typical VPS case where the public IP *is* the server's address. Our control plane sits behind two layers of NAT (the Multipass network, then the host's network), so the detected address was the host network's public IP — the first generated domain for a test app resolved to it, left the machine, and never reached the VM. A hostname does two jobs here: DNS decides which machine a request reaches (sslip.io/traefik.me just embed the IP in the name, and work with private IPs too), and Traefik matches the request's `Host` header against its router rules to decide which app gets it. Both have to agree, which is why fixing it meant changing the domain in Dokploy (so it rewrites the Traefik rule), not just curling a different name — a correctly-resolving name with no matching rule gets a Traefik 404. The decision: set the Server IP to the control plane's Multipass IP, so generated domains are reachable from the host out of the box. Since that IP changes on every rebuild, it can't be set once by hand: it belongs in the script chain (the API exposes `settings.updateServerIp` with `{"serverIp": "..."}`), run on every bootstrap right after the API key exists. The alternative — a real domain with public DNS — isn't available for a laptop lab, and hand-editing each app's domain doesn't survive a rebuild. Note that these domains are only reachable where the VM network is (inside WSL on a WSL host; `forward.sh` only forwards Dokploy's own port 3000, not Traefik's port 80).

## Reachability checks bypass DNS

Wildcard-DNS names like `<app>.<ip>.sslip.io` are convenient for humans, but they make every request depend on two things outside the project: the sslip.io service, and whatever DNS resolver the host network hands out. The second one bit us: the same app domain resolved on one network and failed with `Could not resolve host` on a home network, because many home routers enable **DNS rebinding protection**, which drops any public name whose answer is a private address (`10.x`, `172.16–31.x`, `192.168.x`). That's a sensible security default (it blocks attacks where a malicious site's domain suddenly points at devices on your LAN), and it's exactly the pattern sslip.io relies on. A public resolver returned the right answer and the request succeeded, so the cluster was fine — only name resolution on that network wasn't. The decision: anything scripted that checks reachability (smoke tests in `04` or a later e2e test) pins the name to the control plane's IP itself, with `curl --resolve <host>:80:<cp-ip> http://<host>` or by sending `-H 'Host: <host>'` straight to `http://<cp-ip>`. Both still send the right `Host` header, so Traefik routes exactly as it would for a real client, but the result no longer depends on which network the laptop is on, or on being online at all. Alternatives: hardcoding a public resolver in WSL (`/etc/wsl.conf` + `/etc/resolv.conf`) changes the whole host's DNS; allowlisting sslip.io in the router's rebinding protection only fixes one network; adding `/etc/hosts` entries is manual per hostname. For humans browsing, sslip.io domains remain fine on networks that allow them.
