# Design Decisions

Why things are built the way they are. Each entry: the choice, the alternatives considered, and why. For the build log and bugs found, see [`PLAN.md`](./PLAN.md).

## Provisioning: Terraform stages, driven by `up.sh`

The whole cluster is Terraform, in five stages under [`terraform/`](./terraform), applied in order by `up.sh` and destroyed in reverse by `down.sh`:

| Stage | What it owns | Talks to |
|---|---|---|
| `bootstrap` | the GCS bucket the other stages keep their state in (local state) | GCP |
| `gcp` | network, firewall, static IPs, VMs and their startup scripts, Secret Manager, Cloudflare DNS | GCP, Cloudflare |
| `platform` | the `infrastructure` project: registry, OpenBao, `bao.<domain>` | Dokploy |
| `services` | OpenBao's KV mount and token role, the `infrastructure` secrets provider, the GitHub token, the CI runners | OpenBao, Dokploy |
| `apps/roster` | the example app with its database, Redis, secrets and domain, and CI's credentials on GitHub | Dokploy, OpenBao, GitHub |

It's stages rather than one configuration because a Terraform provider can't be configured with a value created in the same run: the Dokploy provider needs an API key that only exists once Dokploy is installed, and the vault provider a login that only exists once OpenBao has started. Each stage reads the ones before it through `terraform_remote_state` and Secret Manager, and `up.sh` waits between them for what the next one needs (Dokploy answering over HTTPS with its key in Secret Manager, OpenBao healthy, a runner online). Every stage is idempotent, so `up.sh` is also how changes are rolled out.

Alternatives: the previous bash chain (`local/` for Multipass, `remote/` for existing servers over ssh, shared `steps/`) did the same work imperatively, with our own idempotency checks around every API call, and created neither servers nor DNS. The [`vanillauys/dokploy`](https://registry.terraform.io/providers/vanillauys/dokploy/latest) provider (tested against Dokploy v0.30.7 on every release) covers nearly everything those scripts did through Dokploy's API, so what was a hundred lines of `curl` and `jq` per service is now a resource each. What it can't do is listed below; none of it needed a script on the operator's machine. Wrapping the gaps in Terraform `local-exec` provisioners was the other option, and would have been the same scripts with worse error handling.

**State lives in a GCS bucket** (`devops-project-510215-tfstate`, versioned, public access blocked), under one prefix per stage. The states hold secrets (generated passwords, OpenBao tokens), so they can't live in the repo or only on one laptop. The bucket's own stage keeps a local state: it holds nothing secret, and a lost one is a `terraform import` away.

### What isn't Terraform, and where it lives instead

- **Anything that needs to run on a node.** Installing Docker and Dokploy, joining workers to the swarm, the port guard: the VMs' GCE startup scripts (`terraform/gcp/node/`), rendered by Terraform and run by the VM itself on every boot, each step checking before it acts. The operator's machine never ssh's into a node.
- **Dokploy's first admin and API key, and its own domain.** Dokploy has no documented API for creating the first admin, and the provider needs a key to exist before it can do anything. The control plane does it on its first boot (`node/dokploy-bootstrap.py`), against Dokploy on its own loopback, through the same sign-up and tRPC endpoints Dokploy's UI uses: admin from a Secret Manager secret Terraform wrote (with a generated password), key into another secret, where the later stages read it. It then sets Dokploy's domain with `settings.assignDomainServer`, which the provider doesn't cover. The admin has to exist before that: on a fresh Dokploy, whoever opens the UI first can create the owner account.
- **Initializing OpenBao.** Its init call returns the root token exactly once, which Terraform has no clean way to hold. OpenBao 2.7 initializes itself instead (see "Secrets: OpenBao").
- **Placement constraints on an application.** The provider doesn't model a service's Swarm placement. The one we had (the app's replicas on the workers) is gone; see "Web app delivery".
- **Building images.** CI's job, see "Web app delivery".

## Nodes: GCP VMs that set themselves up

One control plane (e2-medium: 2 vCPUs, 4 GB, 30 GB disk) and two workers (e2-small: 2 vCPUs, 2 GB, 15 GB disk), Ubuntu 24.04, in `europe-north1` (Finland: Stockholm, `europe-north2`, was out of capacity). The workers are shared-core, so sustained load gets throttled; `e2-standard-2` is the next step up if CI gets too slow.

- **Their own network, with MTU 1500.** Swarm's overlay networks need 1500 underneath, and GCP's default network uses 1460: large packets between nodes would silently vanish, so image pulls and database replies hang while everything small works. The old chain checked for this; now Terraform defines the network, so it can't be wrong.
- **Fixed addresses.** The control plane's public IP is static, so DNS keeps pointing at it across rebuilds of the VM, and its private IP (`10.10.0.10`) is reserved, because it's the address the workers join the swarm at, and it's baked into their startup scripts. Reserving it matters: an address that's only requested can be handed to another VM created at the same moment (that happened: a worker got the control plane's `.2`).
- **The worker join token goes through Secret Manager.** Workers can't join until the control plane has a swarm, and the token only exists there. The control plane's startup script writes it to a secret, and the workers' scripts wait for it and join. Each role has its own service account that can read (and for the control plane, write) only the secrets its role needs. Alternatives: ssh from Terraform per worker (Terraform's own docs call provisioners a last resort, and it needs the operator's key at apply time), or GCE guest attributes, which another VM can only read through the Compute API anyway.
- **The same Docker version everywhere** (28.5.0, what Dokploy's installer pins), installed by the startup scripts before Dokploy's installer runs, which keeps an existing Docker. Version skew between nodes once made the same command hang on one node and work on another (see "Registry address"), and 28/29 skew can break overlay networking ([Dokploy#4722](https://github.com/Dokploy/dokploy/issues/4722)). Dokploy itself is pinned too, to the release the provider targets.
- **Startup scripts run on every boot,** so each step checks first. Dokploy's installer in particular starts with `docker swarm leave --force`, so it only runs when there's no `dokploy` service yet: re-running it would throw every worker out of the swarm. A changed script reaches a running VM only at its next boot (or `sudo google_metadata_script_runner startup`).

### Closed by default

Dokploy (3000), the registry (5000) and OpenBao (8200) speak plain HTTP, and Docker publishes their ports on every address a node has, past `ufw`. Two layers keep them off the internet:

- **GCP's firewall** only lets in ssh (to every node), 80/443 (to the control plane: Traefik) and Swarm's ports between the nodes.
- **The port guard** (`terraform/gcp/node/port-guard`), a small iptables script run by a systemd unit ordered before Docker, so the ports are never open, even for a moment at boot, and re-run whenever Docker restarts. Published ports are rewritten to a container's address before filtering, so it drops them in `DOCKER-USER` by the port conntrack remembers was asked for, and only new connections, so containers' own outgoing connections to such ports elsewhere still get replies; loopback and Docker's bridges are exempt, which is how the registry at `127.0.0.1:5000` and Dokploy itself still reach them. It also closes Swarm's ports to everything but the cluster's subnet, since Swarm's control traffic and its overlay traffic are unencrypted and unauthenticated respectively. Relying on the provider's firewall alone leaves the cluster exactly as safe as its least careful rule.

What people reach, they reach through Traefik over HTTPS: Dokploy at `dokploy.<domain>`, OpenBao at `bao.<domain>`, apps at their own names. ssh stays open to the internet, since the operator's address changes; the VMs only take key logins.

## DNS and certificates: Cloudflare records, Let's Encrypt through Traefik

`terraform/gcp` creates an A record per hostname (`dokploy`, `bao`, `roster` under `sammosios.com`) pointing at the control plane's static IP, **not proxied** through Cloudflare, so Traefik answers Let's Encrypt's HTTP challenge and terminates TLS itself, with certificates Dokploy asks for per domain. Cloudflare's proxy would add its own TLS in front, and its certificate for the browser, but then Let's Encrypt's challenge needs Cloudflare's settings to cooperate, and every domain would depend on two TLS setups agreeing. The Cloudflare token needs only DNS Edit on the one zone; Terraform takes the zone's id instead of looking it up by name, so it needs no Zone Read.

## Container registry: Swarm stack on the routing mesh, not a Traefik domain

In cluster mode Dokploy needs a registry that every node can pull from. It's a Dokploy compose resource of type **Stack** (a Swarm service, pinned to the manager since its storage volume is node-local), with port 5000 published through Swarm's routing mesh. That makes the registry reachable on every node's own loopback address, `127.0.0.1:5000` (not `localhost:5000`, see [Registry address](#registry-address-127001-not-localhost)), and Docker allows plain-HTTP registries on loopback addresses by default, so nodes need no TLS certificates, no `insecure-registries` entry, and no per-node setup at all. A newly joined worker can pull immediately. The alternative was a Traefik domain with a real certificate, now that there is a domain; but then every pull and push would go out through the control plane's public address and Traefik, and the registry would be on the internet, where the routing mesh keeps it inside the cluster. Traffic between nodes is plain HTTP inside the VPC.

## Registry placement: pinned to the manager node

The registry stores images in a named volume, and named volumes are local to the node they were created on: every node has its own, separate, empty `registry-data`. Without a placement constraint, Swarm is free to reschedule the registry task onto a different node (after a reboot, redeploy, or crash), where it would start healthy but with an empty volume: previously pushed images are silently gone and the next deploy fails to pull. So the registry is pinned to `node.role == manager`: the cluster has exactly one manager, the control plane, and it's the one node that is never removed. The volume therefore lives as long as the control plane's disk; images are rebuildable artifacts, so losing them with `down.sh` is acceptable. The routing mesh means placement doesn't affect reachability. The proper fix is shared storage: the registry supports GCS/S3 storage drivers, which would remove the pinning entirely and allow several replicas, now that the cluster runs where a bucket is one resource away.

## Registry storage: the control plane's disk, 30G

Pinning the registry to the manager puts its images on the control plane's disk. The Ubuntu base plus Dokploy's own images take roughly 4–5 GB before anything is deployed, the registry never deletes old layers by itself (`registry garbage-collect` only frees space after tags are deleted, which is why the stack sets `REGISTRY_STORAGE_DELETE_ENABLED`), and OpenBao and the apps' databases live there too. So the control plane gets 30G while workers get 15G (they run the CI jobs, see "CI runners").

## Registry auth: a generated password, htpasswd through an env var

Port 5000 is open on every node's address inside the VPC, so the registry uses htpasswd auth. `terraform/platform` generates the password (`random_password`, whose `bcrypt_hash` is computed once, so plans stay stable) and hands the htpasswd line to the service base64-encoded in an env var, which the stack's entrypoint decodes to `/auth/htpasswd` before starting the registry. Base64, because a bcrypt hash is full of `$`, which Swarm's compose interpolation would eat. The previous chain created an external Swarm config on the control plane, named after a hash of the credentials because configs are immutable; that needs the Docker CLI on the node, which Terraform doesn't have. The cost: the hash (not the password) is visible in the compose file in Dokploy's UI. The same password goes into Dokploy's registry entry, which Dokploy uses to pull the apps' images and hands to Swarm, and into GitHub, for CI to push. Dokploy's `registry.create` runs `docker login` immediately, and a stack deploy counts as done once Swarm has accepted it, before the container is up, so the entry waits 60 seconds after the stack changes (`time_sleep`). Polling would be better, but port 5000 is closed to the machine running Terraform.

## Registry address: `127.0.0.1`, not `localhost`

The original plan was `localhost:5000`. It worked from every worker, but `docker push localhost:5000/...` from the control plane hung with `Client.Timeout exceeded while awaiting headers`, while `127.0.0.1:5000` answered instantly. The cause is a known Docker bug, [moby/moby#53091](https://github.com/moby/moby/issues/53091) (present since at least 26.x): Ubuntu resolves `localhost` to `::1` first, and the Swarm routing mesh only redirects IPv4, so on Docker < 29.8.0 an IPv6 connection to a published Swarm port lands on a socket `dockerd` holds just to reserve the port, which accepts it and never answers (`ss` shows `dockerd` on `*:5000` with a non-zero `Recv-Q`). It was fixed in Docker 29.8.0 by [moby/moby#53118](https://github.com/moby/moby/pull/53118). Only the control plane was affected at the time because Dokploy's installer hardcodes Docker **28.5.0**, while workers got the latest from `get.docker.com`; every node is on 28.5.0 now, so every node would hang on `localhost`.

Options considered: (a) use `127.0.0.1:5000`, which Docker treats as an allowed plain-HTTP registry like all of `127.0.0.0/8`; (b) pin every node to Docker ≥ 29.8.0, which runs Dokploy on a Docker version it doesn't test; (c) upgrade the control plane's Docker after install; (d) disable IPv6 binding in `daemon.json`, which hides the cause. We chose **(a)**. The cost is one rule to remember: never write `localhost` for the registry (Dokploy settings, image tags, CI workflows). Once Dokploy moves its pin to ≥ 29.8.0, switching back is a config change.

Takeaways:
- **Version skew hides bugs.** The same command worked on one node and hung on another purely because of the Docker version. With every node on the same pinned version (as now), it fails or works the same way everywhere.
- **`localhost` is not the same as `127.0.0.1`.** On modern Linux it usually resolves to IPv6 first, so any IPv4-only component in the path fails in ways a plain IPv4 test never shows.
- **Read what your installer actually does.** The Docker version wasn't a Dokploy setting or documented anywhere; it was a hardcoded, apt-held constant in `install.sh`.
- **Upstream gap.** As of 2026-09-23 there's no Dokploy issue about this; the same 28.5.0 pin is also what breaks Ubuntu 26.04 installs ([Dokploy#5471](https://github.com/Dokploy/dokploy/issues/5471)).

## Services as code: stacks written in Terraform

Every cluster service (registry, OpenBao, CI runners) is a `dokploy_compose` resource of type **Stack** with a **raw** compose file, which Terraform builds with `yamlencode` from an HCL object. Values go straight in, with no template rendering and no placeholder that could reach the cluster unfilled; Swarm's own interpolation still applies, so a literal `$` is `$$`. Dokploy still shows each service, its logs and its deployments in the UI, but the provider owns the whole service: a change made in the UI is reverted by the next apply. Secrets never go in the compose file, since Dokploy stores and shows it. They reach a service as a Swarm secret created on the node (OpenBao's), or as a `${{vault...}}` reference in the compose resource's env, resolved by Dokploy at deploy time (the runners' GitHub token).

Alternatives: a compose resource with a **git** source (Dokploy pulls the file from this repo) would be closer to GitOps, but the repo is private, so it needs a GitHub integration in Dokploy first, which only a person in the UI can create. Swarm-level tools (plain `docker stack deploy`) would skip Dokploy entirely, which defeats the point of running a PaaS.

## CI runners: ephemeral, one per worker, self-registering with a PAT

The repo's CI runs on self-hosted GitHub Actions runners inside the cluster (`terraform/services`). Choices:

- **Image: `myoung34/github-runner`**, pinned by tag. GitHub's own `actions-runner` image has no registration logic, so we'd have to write and maintain an entrypoint that trades the PAT for a registration token, configures the runner and deregisters on shutdown. The tradeoff is trusting a third-party image with the PAT.
- **Registration with a PAT, not a registration token.** Registration tokens expire after an hour, and a Swarm task can restart any time after that. With the PAT, each container fetches its own fresh token when it starts. The PAT is fine-grained: this repo only, Administration read/write, nothing else.
- **The PAT is in OpenBao.** It's a Terraform variable that's both `ephemeral` and written with the vault provider's write-only `data_json_wo`, so it never lands in Terraform's plan or state, only in `secret/infrastructure/github`. The stack's env holds a `${{vault.bao-infrastructure.infrastructure/github:runner_pat}}` reference, which Dokploy resolves when it deploys the stack, and the image's entrypoint un-exports `ACCESS_TOKEN` again, so jobs never see it. This reverses an earlier choice (a Swarm secret, to keep CI independent of OpenBao): Terraform can't create a Swarm secret, and OpenBao is only needed when the runners are deployed, not while they run, so an OpenBao outage doesn't stop CI.
- **Ephemeral runners.** Each container takes one job, deregisters, and exits, and Swarm starts a clean one. No state leaks from one job to the next inside the runner.
- **Swarm global mode on `node.role == worker`.** One runner per worker: adding a worker adds CI capacity without changing any config, and CI load stays off the control plane.
- **The node's Docker socket is mounted.** Jobs build images and push them to the cluster registry at `127.0.0.1:5000`. Docker-in-Docker would isolate jobs better, but needs privileged containers and a separate image cache per runner. The socket makes a job root on its node, which is acceptable for our own repo's workflows, not for workflows from untrusted forks.
- **One finished job container per worker, and 15G worker disks.** Swarm keeps finished tasks as history, 5 per node by default, and each ephemeral runner container holds everything its job wrote (for the web app's test job, about 650 MB: the Go toolchain, modules and build cache). On 10G workers that filled a disk after two jobs. The control plane's startup script sets the swarm's task history limit to 1. The rest of a worker's disk is what the next run reuses: the runner image (3.3 GB), Trivy's database (1.5 GB) and Docker's build cache. With one job running that peaks around 9 GB.

Runners from a destroyed cluster stay listed on GitHub as offline until GitHub removes them (ephemeral runners are cleaned up after about a day).

## Secrets: OpenBao, wired into Dokploy's secrets providers

App secrets live in OpenBao (`terraform/platform`), and Dokploy reads them through its **Secrets Providers** feature (v0.30.0+): an env variable like `DB_PASSWORD=${{vault.bao-myapp.myapp/app:DB_PASSWORD}}` is resolved by Dokploy's server **at deploy time**, and Dokploy's database only ever stores the reference. That answers the question every secrets manager on Swarm has to answer, how a workload gets its first credential: apps never talk to OpenBao, Dokploy does, with one token per provider. Rotating a secret takes a redeploy, since values are only fetched then. Choices:

- **It initializes itself.** OpenBao 2.7's `initialize` config runs a list of API requests on its very first start, as the root token, which it then revokes without ever handing it out. Ours creates a `terraform` policy, enables userpass, and creates the user `terraform/services` and `apps/roster` log in as, with a password read from a file (a Swarm secret the control plane created from Secret Manager). Everything else (the KV mount, the token role, policies, secrets) is Terraform's. So there's no init step, no root token to store, and no window in which an uninitialized OpenBao is reachable: `bao.<domain>` could be public from the first second. Self-initialization requires auto-unseal and produces no recovery keys; recovery keys can be generated later through the authenticated rotation endpoints. The earlier alternative was a script that called `sys/init` and kept the root token in a local file.
- **Single node, Raft storage, pinned to the manager.** Same reasoning as the registry: the volume is node-local and the control plane is the one node never scaled away. Raft rather than the `file` backend because it's OpenBao's recommended storage and supports `bao operator raft snapshot` for backups; `disable_mlock` is on, as recommended with Raft.
- **Static-key auto-unseal.** OpenBao starts sealed after every restart, and a sealed OpenBao fails every deploy that references it. The control plane's startup script generates a 32-byte key from `/dev/urandom` straight into a Swarm secret, so it never leaves the node (not even into Terraform's state), and OpenBao's `seal "static"` reads it from `/run/secrets`. Verified earlier: `docker service update --force` on the running service, and the new task was unsealed within two seconds. The honest cost: the key sits in the same Swarm that holds the data, so anyone who owns the manager owns the secrets. Fine for a lab; production would use a KMS seal, which on GCP is one Cloud KMS key away. The key id (`cluster-1`) must stay paired with the key for the life of the data.
- **Config through `BAO_LOCAL_CONFIG`.** The image's entrypoint writes that env var to its config directory as JSON, so the config is `jsonencode` of an HCL object in Terraform, with nothing on the node.
- **Reached by Dokploy over `dokploy-network`, as `http://openbao:8200`,** a fixed alias, since the Swarm service name carries Dokploy's random suffix. Plain HTTP stays inside the overlay. People and Terraform reach it at `https://bao.<domain>`, with a Let's Encrypt certificate. The route is Traefik labels written into the stack, not a Dokploy domain: Dokploy adds a stack's domain labels only when it deploys the stack, and nothing redeploys it after a `dokploy_domain` is created, so the route would be missing until a manual redeploy. The cost is that the domain doesn't show in Dokploy's UI. Every request needs a token, and there's nothing to initialize. It's no longer published on the routing mesh.
- **One provider per project**, from the `project-secrets` module (`terraform/modules/project-secrets`, see [APP-PROJECT-SETUP.md](./APP-PROJECT-SETUP.md)). Each project gets a policy that can read, and list for the editor's autocomplete, only `secret/<name>/*`, a token issued with just that policy, and a Dokploy provider `bao-<name>` assigned only to that project. That's two independent fences: Dokploy refuses to resolve `bao-<name>` from another project (verified: `listSecretNames` from `infrastructure` gets a 403), and even a wrong assignment can't reach another project's secrets. The policy also allows listing the mount root, which shows every project's *name*.
- **Provider tokens are periodic orphans from a token role.** Dokploy stores the token and never renews it. The `dokploy-provider` role issues tokens with a 768h period, no default policy, and only policies matching `dokploy-project-*`; they're orphans, so they outlive the Terraform login that created them. Unrenewed, a token expires 32 days after it was issued. Every Terraform apply within 14 days of that renews it (`renew_min_lease`), so a cluster that sees `up.sh` at least every two weeks keeps working.

Found while building it: Dokploy's Test Connection validates the token with `auth/token/lookup-self`, which normally comes from OpenBao's `default` policy. With `token_no_default_policy` the test failed with a bare `token validation failed (status 403)`, while reads would have worked. The project policy grants `lookup-self` alone rather than all of `default`. Also verified end-to-end: a stack with `GREETING=${{vault.bao-demo.demo/app:GREETING}}` started with the real value, and `compose.one` still returned only the reference.

**Where values do end up.** "Never in Dokploy's database" is true, but resolved values aren't nowhere: for a compose deploy they're written to `/etc/dokploy/compose/<app>/code/.env` on the control plane and land in the Swarm service spec (`docker service inspect` shows them). So root on the manager can read every deployed secret. That's inherent to injecting env vars at deploy time. And Terraform's state holds every value Terraform generated or wrote (not the write-only ones), which is why it's in a locked-down bucket.

## Web app delivery: Terraform owns how the app runs, CI owns which image

The example app (`web-app/`) runs in Dokploy as an application with the **Docker** provider: Dokploy pulls `127.0.0.1:5000/roster:<commit>` from the cluster registry and runs it, and never touches the Git repo. The tag is the last commit that touched `web-app/`, never `latest`: the running version is always known, and rolling back means pointing at the previous tag.

**The split.** `terraform/apps/roster` owns everything about how the app runs: the project, PostgreSQL and Redis, the replicas, the env, the domain, the secrets provider. CI (`.github/workflows/web-app-ci.yml`) owns which image runs: on a push to `main` it tests, builds, gates on Trivy, pushes, then calls Dokploy's API (`application.saveDockerProvider`, `application.deploy`) and waits for the app to answer. Terraform ignores the image (`lifecycle { ignore_changes = [docker] }`), so an apply never rolls the app back to an older tag. CI's Dokploy API key and the registry's password reach GitHub as Actions secrets, set by the same stage (with `gh auth token` as the GitHub provider's credentials).

The alternative was GitOps for the tag too: CI commits the new tag to a tfvars file and a second workflow runs `terraform apply`. That leaves an audit trail in git, but costs a bot commit per build, and every CI job would need Terraform's state and credentials for GCP, Dokploy and OpenBao: CI would become a way into the whole platform, where now it holds one Dokploy key and the registry password. Dokploy's own Git flow (it clones, builds and deploys on a webhook) has no place for tests or a Trivy gate, needs its own credential for a private repo, and builds on the control plane next to Dokploy, the registry and the databases.

**On a fresh cluster** the app is created before its image exists, so `up.sh` applies the stage once with `deploy_app = false`, runs the workflow on `main`, waits for it, and applies again. The first image goes through the same path as every later one.

**Secrets.** The app's env holds only `${{vault.bao-roster.roster/app:<FIELD>}}` references for `DATABASE_URL`, `REDIS_URL` and the first admin's `ADMIN_EMAIL`, `ADMIN_NAME` and `ADMIN_PASSWORD`. Terraform generates the database's and Redis's passwords, so Terraform is their source of truth and OpenBao holds the URLs built from them (the previous chain let Dokploy generate them and copied them over). The env also carries `SECRETS_VERSION`, the KV secret's version: a new version changes the env, which redeploys the app with the new values, since Dokploy only fetches them at deploy time. A value edited in OpenBao by hand lasts until the next apply writes Terraform's back.

**Placement.** The database and Redis have volumes, so Dokploy pins them to the manager. The app's replicas have no constraint: Swarm's scheduler places a replica on the node with the fewest tasks of that service, then the fewest tasks overall, and the control plane runs far more tasks than the workers, so replicas land on the workers. It counts tasks, not load, and it doesn't move a replica back after a worker returns from an outage; a redeploy spreads them out again. The previous chain set `node.role == worker` through the API, and the provider has no attribute for it.

**The app isn't a stack** like the registry and the runners. Those are the cluster's own infrastructure. The app is the example of something running *on* the platform, so it's set up the way a Dokploy user would: an application, with Dokploy's own PostgreSQL and Redis services next to it.
